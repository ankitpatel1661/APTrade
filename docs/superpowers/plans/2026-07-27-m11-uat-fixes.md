# M11.1 UAT fixes — goals survive reset, and the Performance screen stops lying

**Branch:** `fix/m11-uat-goal-reset-staleness`, based on `feature/m11-swift-backport-parity` (`ad6de3b`, PR #3)
**Source:** manual iPhone UAT, 2026-07-26/27. Findings proved from the simulator's own `UserDefaults`
plus screenshots, not from source reading alone.

Four defects. F1 is a **user ruling that changes shipped behaviour**; F2–F4 are bugs.

---

## Evidence (do not re-derive — this was established empirically)

With storage showing `portfolioGoals = []` and `cash = $500,000`, the screen rendered:

```
Header  TOTAL VALUE   $500,000.00        <- correct
Card    Value Goal    $100,115.77 / $1,200,000.00 · 8%
Metrics Total Return 0.12% · Sharpe -3.89 · Max Drawdown -0.52%
```

Both card figures are wrong and differently wrong: the goal was deleted from storage yet still
renders, and `currentValue` is the user's **original** $100,000 portfolio — stale through *two*
resets. The entire metric grid is likewise frozen on the first-ever load. The header is correct
because it is driven by `PortfolioViewModel`, which reset does touch.

A previously-published diagnosis claimed a re-appearance would self-heal this. **That was wrong.**
`onAppear()` re-reads the goal unconditionally, so had it run the card would have vanished; it did
not run. `.task` does not re-fire on a tab switch because `TabView` keeps tab content alive.
**No fix may depend on view lifecycle.**

## F1 — Goals survive a portfolio reset (USER RULING, behaviour change)

**Files:** `Sources/APTradeApplication/PortfolioUseCases.swift`, the Kotlin twin in
`shared/src/commonMain/kotlin/com/aptrade/shared/application/`, plus tests on both sides.

Today `ResetPortfolioUseCase` calls `goalStore?.save([])` (`PortfolioUseCases.swift:73`), wiping
every goal. **The user ruled this wrong on 2026-07-27:** resetting starting capital is *"start over
with more money,"* not *"abandon my plan."*

Target: reset $100k → $1M with a $120k value goal set ⇒ the goal **survives**, and the card recomputes
to `$1,000,000 / $120,000 · Goal reached`.

1. Remove the goal-clearing from the reset use case on **both** platforms.
2. **`goalStore` then has no remaining use in that use case — remove the dependency entirely**
   rather than leaving an unused optional. It is currently declared `GoalStore? = nil` with a
   comment saying it defaults that way "so existing construction sites keep compiling"
   (`PortfolioUseCases.swift:58-61`) — exactly the re-armed-bug pattern this project has been
   burned by. Deleting it removes the hazard. Update `CompositionRoot.swift:137` accordingly.
3. **Invert, do not delete,** `Tests/APTradeApplicationTests/GoalUseCasesTests.swift:53-59`
   `test_reset_clearsGoals` → assert goals **survive**, and rename it to say so. Same for the
   Kotlin twin.
4. Update `docs/superpowers/specs/2026-07-25-m11-carry-notes.md`, which records clearing-on-reset as
   intended design (§2.5 and §3.4 both reference it). §3.4's *conclusion* still stands — goal state
   must still re-read on every appearance — but its stated *reason* ("reset clears goals") no longer
   applies. Give it the real reason: a stale `currentValue` renders a wrong percentage.

⚠️ Removing the clear means a goal now outlives the portfolio it was set against. Confirm nothing
downstream assumes goal-vs-portfolio consistency (e.g. a goal whose target is denominated against a
portfolio that no longer exists). State your finding in the report.

## F2 — A reset must reach the Performance screen (D1)

**Files:** `Sources/APTradeApp/PortfolioView.swift`, `Sources/APTradeApp/RootView.swift`

`PortfolioViewModel.reset()` (`PortfolioViewModel.swift:186-192`) clears only its own state.
`performanceVM` is a separate `@State` instance (`PortfolioView.swift:36`; the macOS shell has its
own at `RootView.swift:73`) and nothing notifies it. A grep for
`NotificationCenter|didReset|portfolioDidChange|scenePhase` across `Sources/APTradeApp/` returns
nothing.

The reset menu lives in `PortfolioSummaryHeader` (`PortfolioView.swift:419-426`), which renders
**above** the section picker — so it is reachable *without leaving* the Performance section. That is
why the user saw a frozen card.

Give the shared `PortfolioSummaryHeader` an `onDidReset` callback, fire it **after** the awaited
`viewModel.reset(...)` completes (`PortfolioView.swift:268`), and wire it at **both** hosts
(`PortfolioView.swift` and `RootView.swift:434`). **Wiring only one recreates exactly the class of
asymmetry that produced this bug** — the same trap that left one of the two goal screens self-healing
and the other not.

## F3 — Drop the `.idle` gate so the refresh actually reloads (D2)

**File:** `Sources/APTradeApp/PerformanceViewModel.swift`

`onAppear()` (`:77-81`) re-reads the goal unconditionally but guards the reload:
`if case .idle = state { await load() }`. `currentValue` is assigned **only** inside `load()`
(`:107-115`), so it — and the whole metric grid — never refreshes after the first load.

Make `onAppear()` perform a full reload, matching `IncomeSection.swift:46`'s ungated
`.task { await viewModel.load() }`. This is what actually achieves the parity carry-notes §3.4 asked
for, and it reduces F2's fix to a single call.

Watch for a redundant-fetch regression: `load()` is now called on every appearance. Confirm
`loadTask` cancellation (`PerformanceViewModel.swift:33`) makes that safe, and say so in the report.

## F4 — The Value Goal card must be genuinely unconditional (D3, found by the user)

**File:** `Sources/APTradeApp/PerformanceSection.swift`

`content` (`:24-38`) renders `ProgressView()` alone for `.idle` and `.loading`, so the goal card
**does not exist** in those states — despite the doc comment directly above it claiming the card
"must render even before the user holds a single position."

`IncomeSection` does this correctly (`:62-81`): `dripCard` and `incomeGoalCard` sit **outside** the
loading branch, and only the ledger below them switches. Restructure `PerformanceSection.content` to
match — goal card always in the ScrollView, only `reportBody` switching between spinner/empty/loaded.

Third instance of this same Performance-vs-Income asymmetry in one milestone. Fix it to match Income
rather than inventing a third shape.

## Verification

After F1–F4, the reported scenario must produce:

| Step | Expected |
|---|---|
| $100k cash, value goal $120k | `$100,000.00 / $120,000.00 · 83%` |
| Reset to $1,000,000 (without leaving the screen) | `$1,000,000.00 / $120,000.00 · Goal reached` |
| Relaunch, before load completes | Value Goal card visible, not a bare spinner |

Add a view-model test asserting **`currentValue`** — not just `valueGoal` — after a reset. That
assertion's absence is what let this ship.
